# Vault

HA Vault (3 pods, one per AZ, Raft storage, KMS auto-unseal) in `shared-services`.

- `values.yaml`: values of the upstream `hashicorp/vault` chart, version `0.34.1`, pinned in `deploy/argocd/templates/addons/vault.yaml`. The chart is not vendored: a `file://` dependency is impossible, so the pin lives in the ArgoCD ApplicationSet.
- `config/`: chart `vault-config` with the NetworkPolicies (default deny, explicit rules), the hourly snapshot CronJob and the bootstrap Job. It is the second source of the ArgoCD Application because the upstream chart has no hook for extra objects.
- Per-environment values are generated by `tools/config/render_vault.py` from `config/platform.yaml` (`--check` runs in `make lint-repo`): `envs/<env>/<region>.yaml` (upstream chart: KMS alias `alias/<prefix>-<env>-<region short>-vault-unseal` and region as `VAULT_AWSKMS_SEAL_KEY_ID` / `AWS_REGION`) and `envs/<env>/<region>.config.yaml` (this chart: bucket `<prefix>-<env>-<short>-vault-snapshots`, image repository, init secret `<prefix>/<env>/vault/init`, CIDRs). Do not edit them by hand.
- ArgoCD (`addons/vault.yaml`) selects the layer by the cluster labels `payments-platform/environment` and `payments-platform/region`, adds this chart as a second source and passes `requireResolved=true`, so a missing layer or digest fails the render instead of deploying placeholders.
- The only value not in git by hand is the snapshot image digest: CI writes it to `deploy/envs/<env>/images.yaml` under `vault-snapshot.image.digest`, which ArgoCD passes to this chart as a values file. The Vault server image is pinned by version and digest in `values.yaml` (the version of the chart appVersion, the same as the snapshot image).
- AWS access uses EKS Pod Identity (no role annotations): associations `vault/vault` (KMS unseal), `vault/vault-snapshot` (bucket) and `vault/vault-bootstrap` (init secret) are created by Terraform. `roleArn` values exist only for IRSA and stay empty.
- The snapshot bucket (replicated to both recovery regions), its KMS key and the pod identity roles come from Terraform; this directory only consumes their names.
- Namespace `vault` must carry `pod-security.kubernetes.io/enforce: restricted` (set by the namespace owner).
- The vault namespace needs `system:auth-delegator` for the server service account (the upstream chart creates it) so the Kubernetes auth mount can review tokens.

## Operations

- Bootstrap: `bootstrap.yaml` is an ArgoCD PostSync hook Job (service account `vault-bootstrap`, same image as the snapshot, `backoffLimit: 0`). If Vault is initialized it does nothing. Otherwise it first proves it can write the init secret (and refuses to overwrite real recovery keys), then runs `vault operator init -recovery-shares=5 -recovery-threshold=3`, stores only the recovery keys JSON (`recovery_keys_b64`) in Secrets Manager `<prefix>/<env>/vault/init`, and, with the root token held in memory only, in this order: enables the stdout audit device, KV v2 at `secret/` (`max_versions` from `bootstrap.kvMaxVersions`, default 10, `delete_version_after=0s`), Raft autopilot (`bootstrap.autopilot.*`: cleanup of dead servers, 24h last-contact threshold, min quorum 3, 30s stabilization), policies `vault-snapshot` (read `sys/storage/raft/snapshot`) and `external-secrets` (read `secret/data/*`), the `kubernetes` auth mount with roles `vault-snapshot` and `external-secrets`, then revokes the root token (also on failure, via a trap). Keys and token are never logged or written to disk.
- If the Job fails after `init`, a retry sees an initialized Vault and does nothing, so the failure stays visible on the Job: finish the configuration by hand with a root token generated from the recovery keys (see Break-glass). If it fails before the keys are stored, Vault is initialized with no recovery keys: wipe the Raft volumes and sync again.
- Other clusters of the VPC reach Vault at `https://vault.<zone>:8200` (External Secrets layer). Their Kubernetes auth needs a mount per cluster; this Job configures only the local cluster.
- The Raft file does not shrink by itself; if it ever grows, restore the latest snapshot into a fresh node. etcd defrag does not apply (Vault uses Raft, EKS etcd is managed by AWS).

## Break-glass

- No human holds standing Vault access: the `root` token is revoked after bootstrap and no static admin policy is bound to a person.
- Access is requested through the IdP (OIDC, MFA required), approved by a second person, and granted as a Vault policy with a TTL of at most 1 hour that cannot be renewed.
- Every login, token creation and secret read is written to the audit device (stdout of the Vault pods, shipped to the central log store); a break-glass use opens an incident that is reviewed within one working day.
- If OIDC is down, a root token is generated from the recovery keys (`vault operator generate-root`; the keys are in Secrets Manager `<prefix>/<env>/vault/init`, read only with an audited, approved role, threshold 3 of 5) by at least two custodians, used for one session, and revoked at once; the event is recorded the same way.
